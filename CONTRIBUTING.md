# CONTRIBUTING

Цей документ описує правила та процес внесення змін до **psyadapt** — бібліотеки для оцінювання надійності психодіагностичних методик (CSV/XLSX → JSON/XLSX звіти + CLI).

Мова проєкту: **українська** (документація та приклади — українською).  
Код та назви публічних функцій — англійською (стандарт для Python-бібліотек).

## 1. Швидкий старт для розробника

### Вимоги
- Python: 3.10+ (рекомендовано 3.11)
- pip
- OS: Windows / Linux / macOS

### Клонування та dev-інсталяція
```bash
git clone <repo_url>
cd psyadapt
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux/macOS
source .venv/bin/activate

pip install -U pip
pip install -e .
```

> Важливо: CLI-тести запускають **підпроцес** `python -m psyadapt`.  
> Тому для стабільних тестів у “чистому” середовищі потрібен саме `pip install -e .`, а не лише pytest-конфіг `pythonpath=["src"]`.

### Запуск тестів
```bash
pytest
```

Якщо хочеш подивитися CLI “вручну”:
```bash
python -m psyadapt --help
python -m psyadapt data/leary/leary_interpersonal.csv --pretty
python -m psyadapt data/leary/leary_t1.csv data/leary/leary_t2.csv --primary cohen --pretty
```

## 2. Структура репозиторію

Типова структура (спрощено):
```
src/psyadapt/
  __init__.py              # публічний API
  __main__.py              # entrypoint для python -m psyadapt
  cli.py                   # аргументи CLI
  compare.py               # compare_reliability_csv(...) + збір JSON report
  export_excel.py          # XLSX-експорт + стилі + conditional formatting
  validate.py              # перевірки CSV/XLSX
  io/
    __init__.py
    csv.py                 # читання CSV, вирівнювання ратерів, item names
    excel.py               # читання XLSX + конвертації (в т.ч. вертикальний формат)
  reliability/
    base.py                # BaseReliabilityEstimator (sklearn-style)
    cronbach.py
    cohen.py
    fleiss.py
    krippendorff.py
    icc.py
    auto.py                # AutoReliability (вибір метрики за кількістю ратерів/шкалою)
tests/
scripts/                   # manual smoke tests / генератори псевдо-даних
pyproject.toml
README.md
LICENSE
```

## 3. Публічний API: правила сумісності

Все, що експортується у `src/psyadapt/__init__.py`, вважається **публічним API**.
Правила:
- не ламаємо сигнатури без необхідності;
- якщо потрібна зміна — робимо deprecation (попередження) і мінімум 1 реліз переходу;
- публічні функції повертають **стабільну JSON-схему** (ключі не “пливуть”).

## 4. Стиль коду та якість

### Форматування
- Дотримуйся PEP8 (довжина рядка ~88–100).
- Анотації типів бажані.
- Не додавай “магію” в `__init__` класів-оцінювачів: обчислення лише у `fit()`.

Якщо в проєкті є форматер/лінтер (black/ruff) — використовуй його. Якщо немає, залишай код акуратним та однорідним з існуючим стилем.

### Принципи реалізації
- Estimator-стиль: `__init__` → параметри, `fit(X)` → обчислення, `score()` → float, `report()` → dict.
- Для IO: функції мають бути **детерміновані**, без “магічних” змін файлів.
- Для Excel: не роби важких імпортів на верхньому рівні, якщо колись винесемо Excel у extra.

## 5. Тести: що обов’язково перевіряємо

### Мінімальний набір
- `compare_reliability_csv(...)`:
  - 1 CSV → CronbachAlpha
  - 2 CSV → Cohen + ICC
  - 3+ CSV → Fleiss або Krippendorff (залежно від правил авто-вибору)
  - примусовий `--primary` / `primary=` (auto/cohen/fleiss/krippendorff/cronbach/icc — якщо підтримується)
- Excel-експорт:
  - файл створюється, листи названі стабільно
  - item names не перетворюються на Q1..Qn
  - conditional formatting не ламає workbook
- CLI:
  - `python -m psyadapt ...` повертає 0 на валідних даних
  - повертає non-zero на критично невалідних (наприклад, 1 CSV + `--primary krippendorff`)

### Важливо про CLI-тести
CLI-тест — це subprocess, він **не бачить** pytest-налаштувань `pythonpath`.  
Тому в CI треба або:
- робити `pip install -e .` перед `pytest` (рекомендовано), або
- налаштовувати PATH/PYTHONPATH у workflow (гірше і менш прозоро).

## 6. Дані та приватність

Проєкт орієнтований на роботу з психологічними даними.
Будь ласка:
- не коміть реальні дані респондентів;
- для тестів використовуй синтетичні набори або сильно знеособлені;
- якщо додаєш приклади — мінімізуй ризик ідентифікації (без ПІБ/контактів/унікальних маркерів).

### 6.1 Секрети (API keys) і `.env`

У проєкті є **опціональний** AI-модуль, який може використовувати зовнішній API.
Тому для локальної розробки інколи потрібні ключі доступу.

Правила:
- **ніколи не коміть** ключі/токени у репозиторій;
- для локальних запусків використовуй змінні середовища або `.env`;
- `.env` має бути проігнорований git (дивись `.gitignore`).

Підтримувані змінні середовища (для OpenAI):
- `PSYADAPT_OPENAI_API_KEY` (пріоритет)
- `OPENAI_API_KEY`

Рекомендація: скопіюй `.env.example` → `.env` і встав ключ лише локально.

### 6.2 AI-інтерпретація (опціонально)

AI-інтерпретація **вмикається тільки вручну**:
- CLI: додай прапорець `--ai`
- Python API: `ai=True`

Важливо:
- у prompt **не додаємо сирі дані респондентів**; лише агреговані метрики та діагностику пунктів;
- будь-які мережеві запити мають бути загорнуті так, щоб **не ламати** основний пайплайн (AI — це «доповнення», а не критичний шлях);
- юніт-тести мають бути **офлайн**: використовуй `monkeypatch` для мокання `urllib.request.urlopen` (див. `tests/test_ai.py`).

Типові помилки під час локального тесту AI:
- **HTTP 401** → неправильний ключ
- **HTTP 429** → квота/білінг
- **HTTP 404** → модель недоступна (зміни `--ai-model`)

## 7. Як додати новий “естіматор” (метрику)

1) Додай модуль у `src/psyadapt/reliability/` (наприклад, `my_metric.py`).  
2) Реалізуй клас у стилі `BaseReliabilityEstimator`:
   - `fit_info_`, `score_`, `details_`, `warnings_`
3) Додай в `AutoReliability` (якщо потрібно авто-вибір).  
4) Додай інтеграцію в `compare.py` (пер-item, summary, results).  
5) Додай експорт у Excel (якщо метрика має per-item).  
6) Напиши тести (unit +, за потреби, CLI).

## 8. Excel: правила для “читабельності”

- Числові значення мають мати адекватний `number_format`.
- Включай freeze panes + autofilter для таблиць.
- Умовне форматування роби акуратно (перевір у Excel, LibreOffice інколи відображає інакше).
- Не записуй у клітинку типи, які Excel не підтримує (list/dict) — конвертуй у рядок.

## 9. Git workflow: гілки та PR

### Рекомендований процес
- `main` — стабільна гілка
- `feature/<short-name>` — для нової фічі
- `fix/<short-name>` — для багфікса

### Перед PR
- `pytest` проходить локально
- якщо є manual scripts — прогнати відповідні smoke-тести
- не коміть тимчасові файли (`.xlsx` у reports, `.venv`, `__pycache__`, великі архіви тощо)

### Опис PR
У PR додай:
- що змінено
- як протестовано
- якщо змінювалась схема report — які ключі/формати

## 10. Версіонування та релізи

Поки проєкт на ранній стадії, достатньо простого SemVer-підходу:
- `0.1.x` — сумісні зміни/багфікси
- `0.2.0` — потенційні breaking changes (погоджувати окремо)

Реліз чекліст:
- оновити версію у `pyproject.toml`
- оновити `CHANGELOG.md`
- переконатися, що `pip install -e .` + `pytest` проходять
- перевірити `python -m psyadapt --help`

## 11. Де обговорювати питання

- Для багів: GitHub Issues (додай мінімальний приклад + версії Python/OS).
- Для фіч: Issue з коротким user-story “для психолога” + технічним описом “для розробника”.
